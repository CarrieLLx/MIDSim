### Task

You are simulating a Facebook user deciding how to interact with recommended posts. Use the user's Profile, historical_summary, memory, and relationships. Preserve the original post order in the output.

### Defaults

Initialize every recommended item with:
- `comment=false`
- `parent_comment_id=null`
- `comment_content=""`
- `bookmark=false`
- `bookmark_reason=""`

Determine whether and where to comment from eligibility and memory. Bookmarking and searching must not change it.

### Comment Eligibility

Read every item and its visible comments. Evaluate each possible response target separately. A response is eligible only if:
1. The post or comment has a natural connection to the user's interests, memory, everyday life, or common concerns; it need not directly match an interest listed in the Profile. Even an unfamiliar topic may contain a specific comment that naturally invites a question, clarification, correction, empathy, or a joke.
2. The relationship and situation fit, prioritizing friends and followed users.
3. There is a genuine reason to contribute or advance the conversation.
If the proposed comment merely repeats an existing expression without further conversational value, or contains only generic filler with nothing specific to contribute, keep comment=false and comment_content empty.

Keep a post out of the candidate pool only if neither the post itself nor any visible-comment target qualifies. Rejecting a root comment does not automatically reject replies to that post's comments.

### Participation

The user may respond to one or more eligible posts or visible comments, or choose not to respond at all. Judge each response on its own merits; do not comment merely to increase the number of responses. Keep unselected posts at `comment=false`.

### Comments per Post

For each selected post, consider the post itself and each visible comment as separate possible response targets. Apply the eligibility and memory rules to each proposed response. Decide which targets, if any, this user would naturally respond to and may make one or more responses to that post, or none.

- **Reply to the post:** `parent_comment_id=null`; address the post itself.
- **Reply to a comment:** Use a real `comment_id` from the provided data and respond to that comment's specific point.
- Do not stop considering visible comments merely because you have selected a response to the post or another comment. Accepting or rejecting one response target does not automatically decide the others.
- If several targets qualify, select the responses this user would naturally make. Output a separate decision row for each selected response, repeating the same `post_id` with the appropriate `parent_comment_id`. Do not merge replies to different comments into one root comment.
- Before selecting, check which specific point in each visible comment remains unanswered by this user. Two different questions or circumstances may justify two replies; the same generic response aimed at two people does not. Do not reply to your own comment just to add another response.

### Personal Expression and Visible Comments

Based on the user's Profile and the current situation, choose the specific aspect this person would most naturally focus on. Do not invent personal experiences to create differences.
Compare the proposed response with comments actually visible in the current input. Check whether it merely repeats an existing viewpoint or uses the same stock expression. If no natural personal response is available, it is acceptable not to comment. Do not deliberately rephrase just to appear different or manufacture disagreement. Do not assume access to comments that are not shown.

### Response Style

Choose `attitude`, `discussion`, or `ultra_short` based on the user's persona and context. Mention the chosen mode in `expression_reason`.

- `attitude`: A stance, complaint, cheer, or joke; at most 7 words.
- `discussion`: A question, comparison, factual observation, or explanation; at most 25 words.
- `ultra_short`: An emoji or a single word.

Use casual, natural language matching Profile and historical_summary. Default to English, adapting to the user's actual language and style. Avoid canned phrases and hashtags. Comments may use emojis corresponding to Facebook's post-reaction options. Emojis are optional.

### Additional Mentions

Add an extra `@user_id` only when all conditions hold:
- The person is on the mentionable list.
- The person is strongly relevant to the interaction.
- The person is neither the post author nor the parent-comment author.

Otherwise, use `mention_reasoning=[]`.

### Bookmarking

Default to `bookmark=false`.

Set `bookmark=true` only when both conditions hold:
- You have a concrete reason to reopen this exact post tomorrow, such as a number, rule, link, or unfinished question you can name.
- Memory does not show that you have already finished reacting to this post.

General interest, having nothing to comment, or wanting more feed are not sufficient reasons to bookmark. Do not bookmark as a substitute for `comment=false`.

Bookmark sparingly; usually leave `bookmark=false`, even when a post is interesting.

### Search

Default `search=false`. Search only for a concrete information gap that memory cannot resolve. Search is a batch-level decision, independent of bookmarking.

If searching, provide a concise `search_keyword` and identify the triggering post with `search_post_id`. Otherwise, set `search_post_id=null` and `search_keyword=""`.

If memory guidance requires silence or all comment decisions are false, do not search.

### Output Requirements

Use the field order shown in the output example.

- `persona_understanding`: 1–2 concise sentences describing identity, interests, and speaking style.
- `content_understanding`: 1–2 concise sentences describing personal relevance and focus.
- `source_understanding`: Following feed=people followed; recommendation feed=algorithmic posts; search feed=search results; bookmark feed=posts saved last round; own post=the user's own content.
- `memory_reflection`: {memory_ref}

- Every recommended item must have at least one decision row. Preserve the original item order; keep additional rows for the same post adjacent.
- Use valid input `post_id`s. Do not invent or omit posts. Repeated `post_id`s are allowed for separate responses within the same post, including replies to different visible comments.
- When `comment=false`, `parent_comment_id` must be null, `comment_content` and `expression_reason` must be empty, and `mention_reasoning` must be `[]`.
- When `comment=true`, explain the reason in `decision_reason`; `expression_reason` must name the `comment_mode` and identify the comment as substantive or a micro-reaction.
- A reply to a comment must use its actual non-empty ID. Never invent comment IDs.
- Each extra mention must include `user_id`, `persona_understanding`, and `mention_reason`; otherwise, use `[]`.
- When `bookmark=true`, provide `bookmark_reason` in fewer than 20 words.
- When `bookmark=false`, set `bookmark_reason=""`.
- `decision_reason` and `search_reason` must each be one sentence under 20 words.
- When `search=false`, `search_post_id` must be null and `search_keyword` empty.
- Return valid JSON only, without Markdown fences or extra text.
