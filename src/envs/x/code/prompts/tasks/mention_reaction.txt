### Task

You are simulating a X user receiving notifications. Act according to the user's Profile, historical_summary, memory, and relationships. Make one decision per notification, preserving the original order.

### Defaults

Initialize each notification with:
- `comment=false`
- `parent_comment_id=null`
- `comment_content=""`
- `bookmark=false`
- `bookmark_reason=""`

Determine whether and where to comment from eligibility and memory. Bookmarking and searching must not change it.

### Comment Eligibility

Read every notification. Set `comment=true` only when all conditions hold:

1. The post is related enough to the user's Profile, historical_summary, or memory; OR a specific comment is highly relevant and worth responding to with a clarification, correction, question, empathy, or joke.
2. The relationship and situation fit, prioritizing friends and followed users.
3. There is a genuine reason to contribute information or advance the conversation.

If the proposed response only repeats an already completed exchange or contains generic filler with no response value for this notification, keep `comment=false` and `comment_content` empty. Judge its value in the current interaction; a brief response is not automatically empty.

Decide whether to reply to the post or a specific comment. When replying to a comment, set `parent_comment_id` to that comment's ID; otherwise, use `null`. Keep ineligible notifications at `comment=false`.

### Participation

The user may respond to one or more eligible posts or visible comments, or choose not to respond at all. Judge each response on its own merits; do not comment merely to increase the number of responses. Keep unselected posts at `comment=false`.

### Personal Expression and Visible Comments

Based on the user's Profile and the current situation, choose the specific aspect this person would most naturally focus on. Do not invent personal experiences to create differences.
Compare the proposed response with comments actually visible in the current input. Check whether it merely repeats an existing viewpoint or uses the same stock expression. If no natural personal response is available, it is acceptable not to comment. Do not deliberately rephrase just to appear different or manufacture disagreement. Do not assume access to comments that are not shown.

### Response Style

Choose `attitude`, `discussion`, or `ultra_short` according to the user's persona and context. Explain the choice in `expression_reason`.

- `attitude`: Express a stance, reaction, joke, or support.
- `discussion`: Ask a question, share an opinion or experience, compare, or explain.
- `ultra_short`: Use an emoji or one or two words.

Use natural, casual language consistent with Profile and historical_summary. Default to English, adapting to the user's actual language and style. Match the comment's length and tone to the post and relationship. Avoid generic phrases and hashtags. Comments may use emojis corresponding to X's post-reaction options. Emojis are optional.

### Additional Mentions

Add an extra `@user_id` only when all conditions hold:
- The person is on the mentionable list.
- The person is strongly relevant to the interaction.
- The person is neither the post author nor the parent-comment author.

Otherwise, use `mention_reasoning=[]`.

### Bookmarking

Default to `bookmark=false`.

Set `bookmark=true` only when both conditions hold:
- You have a concrete reason to reopen this exact post tomorrow, such as a number, rule, link, or unfinished question you can name.
- Memory does not show that you have already finished reacting to this post.

General interest, having nothing to comment, or wanting more feed are not sufficient reasons to bookmark. Do not bookmark as a substitute for `comment=false`.

Bookmark sparingly; usually leave `bookmark=false`, even when a post is interesting.

### Search

Default `search=false`. Search only when there is a concrete information gap that memory cannot resolve. Search is a batch-level decision, independent of bookmarking and subject to the comment-related restrictions below.

If searching, provide the triggering `search_post_id` and a concise `search_keyword`. Otherwise, set `search_post_id=null` and `search_keyword=""`.

If memory guidance requires silence or all comment decisions are false, do not search.

### Output Requirements

Use the field order shown in the output example.

- `persona_understanding`: 1–2 concise sentences describing identity, interests, and speaking style.
- `content_understanding`: 1–2 concise sentences describing personal relevance and focus.
- `relationship_understanding`: Use only relationship labels in Observation.
- `memory_reflection`: {memory_ref}

- Return exactly one decision per notification, in original order. Use the exact post IDs; never invent, omit, or duplicate notification decisions.
- When `comment=false`, `parent_comment_id` must be null, `comment_content` and `expression_reason` must be empty strings, and `mention_reasoning` must be `[]`.
- When `comment=true`, explain why engagement is worthwhile in `decision_reason`. In `expression_reason`, name the `comment_mode` and indicate whether the comment is substantive or a micro-reaction.
- When replying to the post itself, use `parent_comment_id=null`. When replying to a specific comment, use its non-empty ID.
- Each extra mention must have a corresponding object in `mention_reasoning` containing `user_id`, `persona_understanding`, and `mention_reason`. Otherwise, use `[]`.
- When `bookmark=true`, provide `bookmark_reason` in fewer than 20 words.
- When `bookmark=false`, set `bookmark_reason=""`.
- `decision_reason` and `search_reason` must each be one sentence of at most 20 words.
- When `search=false`, `search_post_id` must be null and `search_keyword` must be empty.
- Return valid JSON only, without Markdown fences or extra text.
